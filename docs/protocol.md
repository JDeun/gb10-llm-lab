# 벤치마크 프로토콜 v0.1

## 범위

기본 범위는 **단일 GB10 + 기존 내장 SSD 1TB**입니다. 실제 RAM, free bytes, 드라이버와 엔진은 inventory 후 확정합니다. 외장 SSD·추가 GPU·여러 GB10은 별도 실험 범위입니다. 사용자가 범위를 바꾸면 이전 결과와 구분해 기록합니다.

## 세 가지 최대치

- **실행이 확인된 최대 모델:** 지정 입력·출력 작업을 수행하고 메모리·I/O와 완료 상태를 기록한 전체 모델.
- **품질을 평가한 최대 모델:** 고정 평가 세트와 채점 규칙으로 완료율과 정확성을 측정한 모델.
- **사용 조건을 만족하는 최대 모델:** 사전에 고정한 품질·속도·TTFT·컨텍스트·오류율 조건을 모두 만족한 모델.

미평가 항목이나 null 기준은 통과가 아닙니다. 조건이 없을 때는 모델 크기–품질–속도–컨텍스트의 비교표와 비지배 후보를 제시합니다. 다른 후보가 같은 작업에서 더 좋은 품질과 속도를 모두 보이는 경우 등을 구분하되, 서로 다른 workload를 한 순위로 섞지 않습니다.

최대 파라미터 값은 체크포인트 범위를 정의한 뒤 비교합니다. 총/활성 파라미터, lookup table/Engram, drafter와 vision 구성 요소를 구분하며, SSD 파일 크기를 파라미터 수의 대용 지표로 쓰지 않습니다.

## 비교 축

| 비교 | 바뀌는 것 | 해석 |
|---|---|---|
| 규모 탐색 | 모델, 양자화, 지원 엔진 | 장비에서 가능한 선택지 탐색 |
| 정밀도 비교 | 같은 모델의 양자화 | 품질·용량·속도 절충 |
| 실행 최적화 | 같은 artifact의 캐시·스케줄링·연산 배치 | 동일 모델의 실행 개선 |
| 모델 근사 | 전문가 삭제, 활성 수 축소, 가중치 생략 | 별도 모델/계산 조건 |

최대 규모 탐색에는 저비트 양자화를 허용합니다. 같은 모델의 속도 최적화에서는 체크포인트·resident 정밀도·활성 전문가 수를 고정합니다. Qwen과 Kimi의 점수 비교를 Kimi 양자화의 품질 보존율이라고 부르지 않습니다.

## 단계와 중단 이유

1. 장비 확인: RAM·MemAvailable·SSD free bytes·실행 환경을 기록.
2. 현재 모델: API, reasoning/answer 분리, usage, 종료 상태를 확인.
3. 후보 적합성: immutable revision·해시·엔진 지원·임시 공간 계획 확정.
4. 실행 단계: 동일 짧은 입력, 출력 상한 1/16/64/256을 순차 증가.
5. 컨텍스트 단계: 입력 길이와 출력 길이를 따로 변경. 목표 512/2K/8K는 탐색점이며 성공 보장이 아님.
6. 품질 단계: 문제 ID와 채점기, 토큰/시간 예산을 고정.
7. 최적화: 한 번에 한 변경, 유망한 후보만 교차 반복.
8. 지속 실행: 최종 후보를 30분 이상 검증하고 변동/실패를 기록.

실패는 `storage_insufficient`, `unsupported_architecture`, `allocation_failure`, `oom`, `timeout`, `transport_error`, `incomplete_answer`, `wrong_answer` 등으로 기록합니다. 일부 요청만 완료한 run을 전체 완료로 판정하지 않습니다. 실패한 시도도 결과의 일부입니다.

## 정확성의 분모

다음 수를 보존합니다.

- N: 계획한 요청 수
- A: 시도한 요청 수
- C: 완성된 최종 답변 수
- G: 정답 판정이 가능했던 답변 수
- K: 정답 수

모든 요청에 기대 정답이 있을 때, 실행 coverage=A/N, 완료율=C/A, 조건부 정답률=K/G, **예산 내 성공률=K/A**를 함께 표시합니다. 기대 정답이 없는 성능 프롬프트가 섞이면 평가 대상 분모를 별도로 사용합니다.

추론 중 제한에 도달한 응답은 완성 오답과 구분하지만, 예산 안에 문제를 해결하지 못했다는 사실을 성공률에 반영합니다. 중도 종료로 A<N인 run은 확인 실험의 가용성 판정에 사용하지 않습니다.

소표본의 조건부 정답률을 정밀한 일반 능력 수치로 해석하지 않습니다. 최종 평가에서는 표본 수와 신뢰구간을 함께 표시하며, 동일 문제/seed 반복을 독립 문제 표본처럼 세지 않습니다.

## 입력과 생성 예산

1/16/64/256토큰 단계는 실행·메모리 경로 확인용입니다. 긴 reasoning 모델의 일반 능력을 평가하기 위한 예산으로 자동 사용하지 않습니다.

- **동일 자원 예산:** 고정 토큰/시간 안에 해결한 비율과 실제 지연.
- **완료 허용 예산:** 모델의 답변 완료를 허용한 상한 아래의 점수와 소요 비용.

둘을 별도 결과로 기록합니다. 초기 클라이언트의 timeout은 소켓 inactivity 한도이므로 wall-clock budget 집행 기능으로 사용하지 않습니다. 시간 예산 비교는 취소를 검증한 실행 감독 기능을 마련한 후 수행합니다.

## 속도·메모리 지표

TTFT(첫 내용 또는 reasoning), 첫 최종 답변 도착 시간, end-to-end 시간, 실제 생성량, 엔진이 보고한 decode 속도를 구분합니다. SSE 이벤트는 토큰 경계가 아닙니다. 엔진이 decode 시간을 주지 않으면 해당 값은 null이며 클라이언트 이벤트 간격으로 대체하지 않습니다.

서버 프로세스가 수집하는 prefill/decode I/O와 expert cache hit rate는 별도 로그로 보완합니다. 러너 telemetry는 **실행 호스트 전체** 카운터이며 다른 프로세스와 파일시스템 캐시 영향을 받습니다. 디스크와 그 파티션 카운터를 중복 합산하지 않습니다.

GB10 통합 메모리는 CPU/GPU를 합쳐 한 번만 계산합니다. 별도 PC에서 API를 호출한다면 그 PC의 inventory를 GB10 서버 메모리로 보고하면 안 됩니다.

## 반복과 재현성

각 후보 1회 탐색 후 유망한 설정만 최소 5쌍의 교차 A/B로 확인하는 것을 목표로 합니다. 매우 느린 모델은 3쌍 탐색으로 방향을 판단하되 작은 표본 한계를 명시합니다. 중앙값·범위와 실제 완료 요청 수를 기록하며 작은 n의 p95를 안정적인 꼬리 지연으로 설명하지 않습니다.

고정할 항목: artifact/엔진 리비전과 dirty patch, 파일 해시, tokenizer/template, thinking, sampling/seed, 입력, 출력 예산, 컨텍스트, 동시 요청, prefix cache 취급.

서버 재시작만으로 파일 캐시가 cold가 되는 것은 아닙니다. 첫 프로세스 요청·warm process 새 입력·warm prefix를 구분합니다. 전문가 profile이 학습/갱신되는 엔진은 사본과 해시를 고정합니다. 상세 profiling 오버헤드는 별도로 확인합니다.
